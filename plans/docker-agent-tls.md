# TLS for the in-container sandbox daemon

NO RETROCOMPATIBILITY

## Goal

Make the connection between jllm and `sandbox-agent.py` (the HTTP daemon inside the sandbox container) confidential and
authenticated when it crosses a network, so a remote Docker host no longer means "SSH tunnel or trusted network only".
Local Docker (loopback, or the exec tunnel for no-network containers) is unchanged.

## Status

Not implemented. Verified in code:
- `sandbox-agent.py` serves plain HTTP. Auth is one header (`X-Jllm-Token`), a random token made per container in
  `ContainerRegistry.create` and passed as the env var `JLLM_TOKEN`; it is visible in `docker inspect` and is read back
  from the container (`ContainerRegistry`, token recovery on reattach; `WorkspaceBackups` blanks it in the committed
  image with `--change "ENV JLLM_TOKEN="`).
- The client side is already half done: `DaemonClient` accepts `https://` in `sandbox.docker.remoteHost`, builds an
  `SSLContext` from `sandbox.docker.trustStore` / `trustStorePassword`, and refuses plain http to a non-loopback host
  unless `sandbox.docker.allowInsecure=true` (warns once per host). So "TLS in front of the daemon" (a reverse proxy)
  already works; what is missing is TLS in the daemon itself and the certificate lifecycle.
- Remote containers publish the daemon port on `0.0.0.0` of the Docker host (`-p 0.0.0.0::<port>`), local ones on
  `127.0.0.1`.
- The agent code reaches a remote host as `JLLM_AGENT_B64` in the env of the container (no bind mount).

## Design

- **Daemon serves TLS** (`ssl.SSLContext`, TLS 1.2+, no client downgrade) when `JLLM_TLS_CERT` and `JLLM_TLS_KEY` (PEM) are
  set. Without them it stays plain and the client rules above apply. Optional mutual TLS: `JLLM_TLS_CLIENT_CA`.
- **Certificate lifecycle, decided here** (the open point in the old TODO):
  - Default: **jllm generates a self-signed certificate per container** at creation (Java side, `KeyPairGenerator` +
    X.509 generation; EC P-256, validity = container lifetime capped at 30 days, SAN = the remote host name/IP).
    **Open point**: the public JDK API has no X.509 builder. Options: `keytool -genkeypair -ext san=...` run as a
    process (needs a JDK, not a JRE; check the distribution), BouncyCastle (new dependency, check size and licence), or
    generating the cert inside the container with Python `cryptography`/`openssl` (key never leaves the container, jllm
    reads back only the public cert and pins its fingerprint; needs `openssl` in the image). The last one is preferred
    when the image has it: it removes the key-delivery problem below. Decide before task 2. The cert and key are delivered to the container as env
    vars (base64) like the agent code, or as a tmpfs file written through `docker exec` so the key is not in
    `docker inspect`; the private key is never logged, never in the committed backup image (blank it like the token).
  - The client **pins the certificate by SHA-256 fingerprint** it generated (kept in memory with the container record and
    in the `BackupRecordStore` entry only as the public fingerprint), through a per-client `TrustManager`. No
    truststore needed for this mode.
  - Operator-supplied alternative: `sandbox.docker.tlsCert` / `tlsKey` (a CA-signed cert for the Docker host name), then
    the existing `trustStore` verifies it. For fleets with their own PKI.
  - Mutual TLS: the generated mode adds a client certificate generated by jllm and trusted only by that container;
    the token header stays as a second factor (defence in depth, and keeps the agent usable without mTLS on a
    loopback).
- **Defaults**: for a non-loopback host, `allowInsecure` defaults to false (already) and the factory now selects TLS
  automatically for remote hosts (`sandbox.docker.remote=true`), so a remote setup works out of the box without the
  operator touching certificates. `allowInsecure=true` remains the explicit opt-out, with the existing warning.
- **Token**: keep it fixed for the container lifetime (it dies with the container), but move it out of the plain env of
  `docker inspect` where possible: with TLS the same `docker exec` channel that writes the key writes the token. At
  minimum, stop logging it and keep it out of images (already the case). Rotation on reattach is optional and not planned.
- **Port binding**: remote containers publish on the Docker host's private interface by default (new
  `sandbox.docker.bindAddress`, default `127.0.0.1` for a host reached over an SSH tunnel; the operator sets the
  private interface for direct access). Never `0.0.0.0` by default.
- **Not in scope**: Docker API TLS itself (`DOCKER_HOST` over `tcp://` with `DOCKER_TLS_VERIFY`; that is Docker's own
  mechanism and stays the operator's job), the exec tunnel used for no-network containers (stays plain: it never leaves
  the machine), the web front end TLS (TODO section 2, web application).

Risks: private key exposure through `docker inspect` or process listing (use exec/tmpfs, test that the key is absent
from `docker inspect`); clock skew on a remote host invalidating the cert (set `notBefore` a few minutes in the past);
Python `ssl` module missing in a minimal image (check at start, fail with a clear message rather than serve plain);
fingerprint pin lost after a jllm restart (reattach re-reads the public cert through the exec channel and re-pins only
if the container's `jllm.config` label matches; otherwise the container is replaced).

## Remaining tasks

1. `sandbox-agent.py`: TLS context from `JLLM_TLS_CERT` / `JLLM_TLS_KEY` (and optional client CA); refuse to start with
   half the pair set; fail clearly if `ssl` is unavailable; keep plain mode.
2. Java: `AgentCertificate` (decided, D8: the EC key and self-signed cert are generated by openssl inside the container,
   the key never leaves it; Java reads the certificate and its fingerprint; optional client cert), delivery of the
   certificate without exposing any key, `DaemonClient` fingerprint-pinning `TrustManager` and optional client key; wire
   into `ContainerRegistry.create` and reattach. Change signatures and fix callers.
3. Settings: `sandbox.docker.tlsCert` / `tlsKey` / `bindAddress` in `DockerSettings` and `HarnessConfig.Docker`
   (settings merge, `SandboxPolicy`, `HarnessSettingsBuilder`), documented defaults.
4. Tests (no Docker, no real Python agent; Windows/Linux/macOS): in-process TLS fake of the daemon in Java (`HttpsServer`)
   proving fingerprint pinning accepts the right cert and rejects another one, mTLS with a wrong client cert,
   plain-http refusal for a non-loopback host, `allowInsecure` opt-out warning, generated cert validity/SAN/`notBefore`,
   settings round trip, private key absent from the container create command line and from the backup image command.
   Python-side TLS test only if the repo has a Python test hook; otherwise a startup self-check in the agent
   (`--selftest`) run by CI where Python exists, never required to build.
5. Docs: `docs/guides/sandbox.md` remote section (what is automatic, the fingerprint pin, the operator-cert variant,
   bind address), `roadmap-and-limits.md` (drop "remote daemon is plain HTTP"), `securing-and-enterprise-setup.md`;
   feed `plans/secdoc.md`. Until this lands, the interim documented rule stays: SSH tunnel or trusted network only.
